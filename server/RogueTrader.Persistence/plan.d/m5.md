# M5 repairs and equipment upgrades — Persistence view

Parent: [Persistence implementation plan](../IMPLEMENTATION_PLAN.md). Queue item M5 in [TASK_QUEUE.md](../../../TASK_QUEUE.md) and [brief](../../../docs/tasks/m5.md). October 27, 2026.

- `RepairAsync`/`RepairRequest`/`TransactionKind.Repair`: a priced, station-gated, idempotent service that debits the wallet only. Hull health is simulation state and the original repair amount/unit/cost (ids 39/40/43, raw f[33] = 5/10/50, buy 0) are undecoded, so the caller applies the repair to the ship and this core records `RepairId` on the result and in the idempotency window. `RepairId` is an optional payload field and the profile schema is now **2** (built-in `ProfileSchemaMigrations.V1ToV2`, applied without caller registration), so a schema 1 reader sees an unsupported newer version instead of quarantining the file as corrupt; schema 1 files load and are rewritten at 2 (tested).
- `IPriceSource.TryGetRepairPrice` has a default implementation (not offered), so existing price sources are unchanged.
- Upgrades keep the existing `BuyUpgradeAsync` path. `StationPriceTable.FromOriginalItems` now prices the original upgrade categories at the raw buy field (Engine/Thruster/Power Mods, Hull Armor, HyperDrive Systems: 35 rows, id = decimal ITM id). Repair prices are never derived from original data; they are authored (NEW/provisional) through `WithRepairPrices`/`WithUpgradePrices`, which are all-or-nothing per batch.
- Finding: the original data names five upgrade groups, not six. The "six equipment upgrades" count in master M2 stays unconfirmed; the six-slot tests use NEW fixture ids. Stacking, exclusivity, slots, effects and installation restrictions remain undecoded.
- Not done: client/UI, applying repair to simulation health, original station inventories. RT-F047/F048/F049 and the master M2 boxes stay open.
