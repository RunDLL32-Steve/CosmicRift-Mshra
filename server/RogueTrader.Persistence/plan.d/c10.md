# C10 recoverable sector transfer model — Persistence view

Parent: [Persistence implementation plan](../IMPLEMENTATION_PLAN.md). Queue item C10 in [TASK_QUEUE.md](../../../TASK_QUEUE.md) and [brief](../../../docs/tasks/c10.md). Master [§11.3 sector transitions](../../../ROGUE_TRADER_2_PLAN.md#113-sector-transitions) and [§14.1](../../../ROGUE_TRADER_2_PLAN.md#141-persistence-requirements) ("sector transfers are recoverable"). November 2, 2026.

Everything here is a NEW engineering design. No original sector, route, gate, spawn or transition rule is encoded; those stay open (RT-F050–RT-F058, RT-F054 warp retention).

## Ownership

-   One durable `PlayerPresence` document per player in an `ITransferJournal` names the single sector that owns the player and a fencing epoch, holds at most one in-flight `TransferRecord`, and keeps the last `TransferOptions.RecentWindow` (NEW, 64) finished transfers for duplicate detection. Every write is a compare-and-swap on the document revision, and `TransferInvariants` refuses a document whose owner and epoch contradict its record's phase.
-   The journal is separate from `PlayerProfile`, so the profile schema stays at its current version and the coordinator never touches wallet or inventory: those stay in the transaction core. A sector's ship, carried cargo and any carried currency travel as an opaque counted `TransferManifest` that the coordinator only compares.

## State machine (`SectorTransferCoordinator`)

1.  Validate shape, identity (`TransferContext`), known and distinct sectors, an optional route policy, registration, owner equals source, nothing in flight. Refusals write nothing.
2.  Journal `Preparing`. The source `Detach`es (freezes) the ship at the journalled epoch; the destination `Reserve`s it at a validated entry (an unknown entry is refused). Journal `Prepared` with manifest and spawn.
3.  **Commit point:** one journal write sets `Committed`, owner = destination and epoch + 1.
4.  Destination `Activate`s, source `Release`s, journal `Completed`. An abort before step 3 journals `Aborting`, then destination `Cancel` and source `Restore`, then `Aborted`.

Recovery (`RecoverAsync`, `RecoverAllAsync` from `ListInFlightAsync`) aborts anything before the commit point and rolls `Committed`/`Aborting` forward. A retry of the same transfer id resumes it; a finished one replays; a different request under a used id is `TransferIdReused`. A coordinator whose write conflicts stops with `Unresolved` and changes nothing further.

`ISectorParticipant` calls are idempotent per transfer id. `Restore`/`Cancel` tombstone the id so a stale coordinator's later `Detach`/`Reserve` is refused, and contradictory decisions throw. `InMemorySectorParticipant` is the reference implementation, with snapshots for restart tests; `InMemoryTransferJournal` is the reference journal.

## Evidence

`tests/Unit/Persistence/SectorTransferTests.cs` (42 cases): happy path both ways; nine validation refusals with no write; invalid spawn and missing source ship abort and restore; duplicate commit retry before and after a coordinator restart; 32 parallel retries apply once; 16 competing transfers move the ship once; two coordinators on one journal; twelve crash points (journal save before/after write at each of the four writes, and detach/reserve/activate/release failures) each settled by recovery after reconstruction and by retrying the same request; a failure while aborting; a second transfer blocked until recovery; stale coordinators fenced before and after the commit point; participant contract refusals; journal invariants; and four seeded soaks of 150 steps over three sectors and three pilots with random journal and participant faults, restarts, retries and recoveries, asserting after every step that each ship is held somewhere, active in at most one sector and unchanged. Two deliberate mutations (no reserve tombstone; activation before the commit point) each fail tests.

## Not done

Wiring into `WorldSimulation`/`AuthoritativeSession` (there is one sector today), a durable file or PostgreSQL journal, transport and disconnect handling, cross-server deployment, and every original transition behavior. No feature checkbox is ticked.
