## 2. inheritedSpeed -550 and aliveTime -65

**f[94] inheritedSpeed.** Distribution over the 92 type-6 rows: 0 ×24, 1000 ×22, -550 ×15, 1200 ×10, 1500 ×8, 550 ×3, 1250 ×3, 1400 ×2, 1600 ×2, 750, 1300, -250 (one each). The fifteen -550 rows are exactly the launched rockets and beams: 1047 MIRV, 1006 Tachyon, 1050 Shrapnel, 1054 Moltor Crystal, 1063 BioMissile Storm, 1072 Moltor Shower, 1077 Rocket Pod, the four ClusterRocket children 1016/1021/1022/1023, and beams 1040 HEL, 1043 Particle Beam, 1069 X-Laser, 1073 Laser Cannon. The only other negative is 1082 Wake Caster-Child -250. Every other zone ITM in the repository uses -550 too (Cyg 4, chaosadvanced 20, core 4, …) and chaosadvanced adds -150.

-   Scale evidence: rogue.cfg line 2125 `[Soccer] DefaultInheritSpeedPercent=1000` (and line 2126 `DefaultInheritZSpeedPercent=1000`) shows this engine writes inherit-speed **percentages as per-mille** with 1000 for 100 %, for the ball. That supports reading positive f[94] (1000, 1200, …) as per-mille, but it is an analogy from another object class: classification UNKNOWN for projectiles, confidence low-to-medium.
-   rogue.cfg line 132 `[Vehicle] InheritSpeedOnDefaultChange=1` concerns vehicles, not projectiles.
-   **Resolution: open.** No read source gives the meaning of a negative value. The pattern (only self-propelled weapons, one shared magic value across zones) suggests a mode rather than a negative percentage, but which mode (for example "ignore ship velocity", or a weighted rule as the RT-F036 title assumes) is UNKNOWN. `OriginalProjectile.InheritedSpeed` keeps -550 and flags it.

**f[110] aliveTime.** Distribution: 2000 ×24, 550 ×17, -300 ×10, 6000 ×7, -2000 ×6, -550 ×5, 100 ×6, 150 ×3, 700 ×3, -65 ×2, -85, -80, -50, -5, -1 (one each), and others. Twenty-eight rows are negative.

-   NWS 1/13/02 (Rogue.nws line 456) "Energy use on X-Laser was increased and projectile life decreased", with X-Laser f[110] 350 against 550 on the other beams, supports f[110] being projectile life. Classification VERIFIED that life changed and that X-Laser's value is lower; not the unit.
-   The two -65 rows are 1047 MIRV and 1063 BioMissile Storm, and both pair f[110] -65 with f[115] inactiveTime 65, f[108] proximityRadius 0 and f[142] a type-8 child (3008, 3012). Other split weapons pair negatives with smaller inactive times: 1072 Moltor Shower -85 / 50 → 3015, 1071 MoltorShowerMd-Child -80 / 10 → 3014, 1050 Shrapnel -2000 / 50 → 3011, 1052 BioShrapnel Bomb -2000 / 0 → 3009. But negatives also occur without any child (1006 Tachyon -2000, 1054 Moltor Crystal -2000, 1077 Rocket Pod -2000, 1053 BioPulse -2000, ten debris chunks -300, four BioCloud children -550, 1070 MoltorShowerSm-Child -550, 1034 LargeExplosion -5, 1080 Orion Booster -50, 101 Repulsor -1).
-   **Resolution: open.** "Negative = explode when life ends" cannot be the whole rule (childless rows are negative too), and "negative = different time unit" is not supported by any read source. Keep -65 raw and flagged; RT-F040's "negative trigger" clause stays unchecked.

CFG `[Vehicle] ExplodeItemDistance=2200` (rogue.cfg line 131) is a vehicle setting. **Resolution: open.** Whether a projectile collides as a point, a circle of proximityRadius, or the graphic's extent is UNKNOWN; hull collision fields are RT-F029. No shape is assumed.

## 5. Type-8 entry fields and offset units

The upstream MultiUse loader reads up to 32 child entries from f[97] with stride 6, named `id, deltaX, deltaY, deltaZ, deltaAngle, multiLinkMode`, with `multiLinkMode` an enum `None=0, Disappear=1, Explode=2`. In the pinned file all 20 type-8 rows have 97 + 6k fields (109 … 193), so every entry is whole.

| Entry field | Upstream name | Non-zero pinned values                                                                                                                       |
| ----------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| +0          | id            | resolves for every non-zero entry                                                                                                            |
| +1          | deltaX        | ±20 on 3005, 3006, 3013, 3016, 3017 and 3019 (3019 left child -20); 3003 +20, +10, -20, -10; 3002 BaseStationCannon ±10; 3018 Wake Caster ±5 |
| +2          | deltaY        | 3002 BaseStationCannon 15, 15; 3018 Wake Caster -25, -25                                                                                     |
| +3          | deltaZ        | none                                                                                                                                         |
| +4          | deltaAngle    | 3008 MIRV Missile-Blast and 3012 BioStorm-Blast -5, -10, -15, 5, 10, 15; 3018 Wake Caster 135, 225                                           |
| +5          | multiLinkMode | none                                                                                                                                         |

-   The field the RT-F040 code called "raw offset" is upstream `deltaAngle`. The paired left/right ±deltaX on "Dual" launchers, and Wake Caster's 135/225 (mirror-symmetric about 180, its child 1082 Wake Caster-Child has f[6] "Defensive system that trails energized pellets behind the triggering vessel"), are consistent with a lateral offset and a heading offset. Units remain UNKNOWN: 135/225 fit degrees, but Infantry also uses other angle scales, and deltaX/deltaY could be pixels or world units.
-   **Resolution: fields identified (parser names), units open.** `OriginalMultiItemEntry` now keeps all six raw ints (`RawFields`) and exposes `DeltaX`, `DeltaY`, `DeltaZ`, `DeltaAngle` and `MultiLinkMode`; `RawOffset` stays as an alias of `DeltaAngle`. This closes the RT-F040 review note (round 4, item 1) that 22 non-zero field-1/2 values were dropped. A non-zero entry cut short by the end of a row now throws instead of being skipped. `OriginalItemReferenceResolver` now names all five entry fields and the seven new projectile fields in its field inventory (labelled as upstream names, raw). Its structural asset-pair heuristic takes up to six trailing ints after a text pair, which on type-8 rows runs past the 3-field firing sound at f[93..95] (upstream `Sound`: blob, id, maxSimultaneous) into the first child entry; a field that is already named now keeps its name, and the pair's raw trailing ints are unchanged.
