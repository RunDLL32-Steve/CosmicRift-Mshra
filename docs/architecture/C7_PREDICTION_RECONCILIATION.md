# C7 controlled-ship prediction and reconciliation

The client predicts the controlled ship's motion between authoritative snapshots. The server receives only `PlayerInput`. The protocol, tick policy and fixtures for this component are **NEW/provisional** testbed groundwork. Master M3 acceptance requires independent clients in a shared world. [C7 task](../tasks/c7.md) · [Master §13.2–3](../../ROGUE_TRADER_2_PLAN.md#132-server-responsibilities) · [Master §18 M3](../../ROGUE_TRADER_2_PLAN.md#milestone-3--dedicated-multiplayer)

## What can be restored

A C5 `WorldSnapshot` identifies a completed server tick and acknowledged input sequence. Its entity records carry position, velocity, rotation, hull and shield. They omit ship definitions, collision radii, reactor energy, weapon cooldowns, projectile allocation, cargo and mining state. C3 replay starts from a complete initial world at tick zero. `RestorePlayer` is a persistence operation that sets velocity to zero. Neither API can reconstruct an arbitrary simulation world from this packet. [Wire records](../../shared/RogueTrader.Protocol/Messages.cs) · [Simulation replay](../../server/RogueTrader.Simulation/Replay/SimulationReplayer.cs) · [Player restoration and tick order](../../server/RogueTrader.Simulation/WorldSimulation.cs)

Bind a predictor to a server-supplied controlled entity ID and matching validated game catalog. Copy its static sector asteroid geometry in catalog order. Supply the local ID explicitly because the wire format contains no ownership flag. Copy the controlled ship record from the accepted snapshot. Use its exact position, velocity and rotation as the motion baseline. Hull and shield retain the server values until the next accepted snapshot. A destroyed ship stays at its snapshot pose. Ship definition or sector changes require a matching prediction context. Code that establishes control must obtain a current baseline and account for any previously outstanding inputs before creating a new predictor. [Catalog validation](../../shared/RogueTrader.GameData/GameCatalog.cs)

Prediction and authoritative flight use the same movement and swept asteroid collision code at `WorldSimulation.TickDuration`. Asteroid traversal order, speed clamp, turn and collision response use the same definition and operation order as the authority. The prediction component steps only motion in its own state. `Fire` travels in the outbound message. The authority owns projectiles, damage, rewards, mining and persistence. [Movement and tick order](../../server/RogueTrader.Simulation/WorldSimulation.cs) · [Swept collision](../../server/RogueTrader.Simulation/CircleCollision.cs)

Keep the client-side state machine in `shared/RogueTrader.Prediction`, which references Protocol and Simulation. The caller can issue one intent, reconcile an incoming snapshot and read the resulting local ship state, predicted tick, accepted server tick, acknowledgement and pending count. The wire codec and authoritative session retain their existing interfaces. One caller serializes input and snapshot processing.

## Issuing an input

A fresh predictor starts at the accepted snapshot tick with an empty pending queue and uses its acknowledgement as the sequence floor. Tick zero requires acknowledgement zero because no server input could have run. The caller supplies a positive maximum number of outstanding predicted ticks. It can choose a bound within the server's accepted lead window. Give each local tick one new `PlayerInput`, with a strictly increasing sequence and client tick, each incremented by one. Stamp the last accepted server tick into `LastSnapshotTick`. The initial unused sequence zero represents C6's pre-input acknowledgement. A tick of neutral controls still advances time and drift. Validate finite thrust/turn within `[-1, 1]` and supported flags before consuming a tick or sequence.

Compute the next motion in scratch state, requiring finite derived position, velocity and rotation before publishing an intent or consuming a tick/sequence. Finite inputs and definitions can still overflow intermediate arithmetic; reject that issue atomically and return no intent. The shared authoritative motion formula is unchanged. Queue the message and advance predicted motion once only after this check. The caller may submit that same immutable message to C6. With a full queue or an exhausted `uint` tick or sequence, decline prediction before changing any state. Capacity becomes available when an authoritative snapshot covers pending ticks. Keeping the last issued sequence independently of the queue prevents reuse after inputs expire. C6 accepts more general per-tick submissions, including multiple sequences, but this predictor emits a single local intent per tick. ## Accepting a snapshot

1. Compare against the **last accepted server tick**. Ignore a repeated or older tick. A snapshot newer than the accepted baseline can still correct earlier ticks within the current prediction window.
2. For an advancing snapshot, require a bounded entity list and exactly one record with the controlled ID. That record must be a ship with finite coordinates, velocity, rotation, hull and shield. Directly constructed messages require the same local field checks as decoded data. Store the controlled record by value so later changes to the caller's entity array cannot change the prediction. [Codec](../../shared/RogueTrader.Protocol/MessageCodec.cs) · [Wire bounds](../../shared/RogueTrader.Protocol/ProtocolLimits.cs)
3. Accept an unchanged acknowledgement, or an advance to the sequence of a retained locally issued input whose named tick has completed by `ServerTick`. Reject a regressing, unknown or premature acknowledgement before changing the accepted tick, sequence, pending inputs or motion.
4. Replace the baseline with the server ship record. Drop every pending input whose named tick is at or before `ServerTick`, even when its sequence exceeds the acknowledgement. C6 runs neutral controls on a missing tick and rejects late submissions. A sequence acknowledgement is a high-water mark and proves nothing about delivery of each lower sequence.
5. Replay remaining inputs once each in ascending `ClientTick` starting immediately after the accepted tick. The predictor emits contiguous ticks, so the remaining inputs form a contiguous suffix. If a snapshot advances beyond every prediction, adopt its pose and tick directly. Replay cost is bounded by the pending queue size even across a large tick jump. Check every derived replay pose for finite motion before committing the correction; return `InvalidMotion` with the old public state, queue, tick and acknowledgement intact if any replay overflows. A subsequent valid correction can retry against the retained queue.

**Example (NEW/provisional fixture).** From tick zero, predict three inputs with sequences 1–3. The server receives input 1, misses input 2 and snapshots after tick 2 with acknowledgement 1. Restore its tick-2 pose, discard inputs 1 and 2, then replay input 3 from that pose. A subsequent snapshot for tick 3 with acknowledgement 3 settles that last input. Replaying input 2 would apply thrust after its server tick expired.

## Acceptance evidence to collect

-   Compare the predicted pose after each queued input to the controlled ship in a real `AuthoritativeSession` given the same inputs. Include reverse thrust, turning, neutral drift and swept asteroid contact. Verify that local prediction leaves the authority untouched until the server accepts and steps the submitted intent.
-   Deliver a delayed snapshot after divergent motion, then check the immediate replayed pose and final convergence. Include a permanently lost input with an unchanged acknowledgement, a missing snapshot, duplicates and out-of-order delivery. Drive the schedule with integer ticks.
-   Exercise an unchanged acknowledgement across a newer snapshot, a jump over lost inputs, a regression, an acknowledgement beyond the last issue, and one issued for a tick later than the snapshot. A rejection must preserve all state, including the original queue so a subsequent valid acknowledgement still works.
-   Check initial snapshot binding, missing/ambiguous/wrong-kind entity, malformed controlled fields, mutated snapshot array, destroyed hull, full queue and recovery, exhausted identifiers, and an authoritative tick ahead of prediction. Include nonzero initial velocity so an accidental use of `RestorePlayer` is observable.
