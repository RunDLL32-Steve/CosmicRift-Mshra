# Rogue Trader 2.0 development conventions

Read `PROJECT_START.md` and the complete `ROGUE_TRADER_2_PLAN.md` before changing scope. The latter is the master specification; Milestones 0 and 1 engineering acceptance is complete. Current work is the exact-reproduction fidelity gate and incremental Milestone 2 work after its dependencies are validated.

- Complete a milestone's mandatory acceptance criteria before starting the next. Keep a compilable, runnable vertical slice.
- Separate pure C# simulation and data definitions from Godot rendering, input and UI. Future networking, persistence and AI remain separate modules. The eventual server is authoritative.
- Use fixed 60 Hz simulation with explicit world units. Never use rendering-node state as authoritative gameplay state.
- Use external JSON definitions. Mark every invented number NEW/provisional. Record historical classifications and source access in `docs/original-research/MECHANICS.md`; never fabricate evidence. Use the user-authorized canonical original content without altering its source bytes; keep derived runtime outputs separate.
- Keep changes small and test critical movement/combat behavior. Run only the focused checks required by a completed feature; reserve simulations for completed gameplay behavior needing verification.
- Maintain `README.md`, `CHANGELOG.md`, `docs/development-log/PROGRESS.md`, the dated log, and each affected folder's `IMPLEMENTATION_PLAN.md`.
- Reconcile subplans with the master: link the exact milestone/section, check off only implemented and verified work, attach evidence, and leave blocked or deferred work unchecked. The master remains the status authority.
- Produce a reproducible Windows artifact at milestone boundaries. A successful source build alone does not prove the exported client launches.
- Prefer simple modules and canonical originals where decoded; keep remaining placeholders explicitly provisional. Do not introduce multiplayer infrastructure or unrelated features before the flight/combat prototype passes acceptance.
- Use the pinned toolchain in `toolchain.lock.json` and `global.json`. Portable dependencies, caches and build artifacts stay ignored in `.tools/` and `artifacts/`.
- Treat fowlmouth/cosmic-rift-assets at the pinned ASSET_MANIFEST commit as the foundational original content source for 100% Rogue Trader reproduction. Never alter original source files, names or values; store derived decoding/adaptation outputs separately and run scripts/verify-reference-assets.ps1. Original data takes precedence over provisional/new proposals. Evaluate InfantryOnline server/native-client compatibility before extending the Godot testbed into a production engine choice.
- Inspect licenses before reusing external code or data. A public repository is evidence of availability, not automatic redistribution permission.

## Maintained agent qualification and review rule — October 14, 2026

- Use agents for independent work that advances the current project goals. Give each agent a bounded task, file ownership, required context and acceptance criteria; avoid overlapping edits and shared-output builds.
- Choose and explicitly set each agent's model and reasoning effort from the "Model and effort matrix" below before spawning or assigning follow-up work. Do not let routine work inherit the top model or Ultra by default; give the reason when deviating from the matrix. When the tool requires a fresh context to set effort, supply the necessary context in that assignment.
- Reassess when an agent's task changes; if the tool cannot change effort, assign the follow-up to a suitably configured agent instead of silently reusing the previous setting.
- The coordinating agent must review every agent's work before accepting or integrating it: inspect the actual changes/findings, verify the relevant evidence and focused checks, and resolve identified defects. An agent's completion claim alone is not acceptance. Record the review outcome with the work's evidence; leave unverified feature checkboxes open.
- Keep this rule in force across sessions and handoffs unless the user explicitly changes it.

## Agent and branch workflow — October 15, 2026

- One scoped branch (and worktree) per issue/feature/fix; inspect existing checkout state first and preserve unrelated uncommitted work.
- **The author never merges their own work into main.** A different, newly started review agent reviews the branch (diff, intent, tests, conflicts) and merges it only if approved. If not approved, the reviewer states why, may fix the change on that branch and then merge; it must not merge anything it has not itself understood. For code the reviewer re-runs the relevant tests (`scripts/verify.ps1`, `prepare-derived-source.ps1` plus runtime/native-delivery checks as applicable) and judges by the JSON reports; the wrappers now cache the process handle, so a blank or non-zero exit is a real failure and the JSON report remains acceptance evidence.
- The orchestrating session runs Sonnet 5.5 at medium effort and delegates per the matrix. The coordinator inspects every agent's actual diff and evidence; a completion claim alone is not acceptance. Leave unverified feature checkboxes open. Diagnostic or WIP branches merge only as clearly labelled tooling and never mark a feature complete.
- At a usage/checkpoint stop, commit owned issue work on its branch first, then record the commit, verified results, incomplete reviews and the exact resume point. Preservation commits never imply completed verification.
- Pushes only to feature branches and only where the user has authorized it (the cloud routines below); never push main directly. The only way cloud work reaches main is the pull-request merge gate in "Cloud routines", which the user authorized on October 15, 2026. No desktop/GUI interaction without the user present.

### Test selection and marking off work

- **Run only the checks that apply to what changed.** Do not run login/native-delivery checks for a weapon change or flight tests for a shop fix. Map the change to its checks:
  - `shared/`, `server/RogueTrader.*`, `tests/Unit` -> `dotnet test tests/Unit` only (plus the Godot smoke in `verify.ps1` only if `client/` or the simulation/physics shared with the client changed).
  - `client/` -> `scripts/verify.ps1` (build, unit tests, Godot import and smoke).
  - `scripts/compatibility/patches/shop-*`, null-script capacity, radar routing, `RuntimeChecks/` -> `prepare-derived-source.ps1` then `run-runtime-checks.ps1 -Build`.
  - `patches/packet-length.ps1`, `NativeDeliveryChecks/`, asset packet code -> `run-native-delivery-checks.ps1 -Mode fixed`.
  - `scripts/compatibility/*native-start*` -> `python scripts/compatibility/test-native-start.py`.
  - Markdown only -> `python scripts/check-trackers.py` and nothing else.
  Run the full set only for a cross-cutting change (shared build props, solution layout, the derived-source pipeline itself) or before a release. Report which checks were skipped and why.
- **Mark off finished work in the same branch that finishes it**, so nobody repeats it: tick the item in `docs/original-research/FEATURE_MASTER_CHECKLIST.md` and `ROGUE_TRADER_2_PLAN.md` section 18, set the catalog row, write the folder plan entry and update `CONTINUATION.md` "Next", and move every status count together. Only tick with verified acceptance evidence; leave anything unverified open and say so. `python scripts/check-trackers.py` must print `TRACKERS_CONSISTENT` before a branch is reviewed or merged, and the reviewer re-runs it.
- **One file per item, never a shared append point.** A branch's per-item status entry for a folder goes in its own new file, `<folder>/plan.d/<lowercase RT-ID or queue id>.md`, not as a line appended to the folder's `IMPLEMENTATION_PLAN.md`. Many branches are in flight at once, and every end-of-file append collides at merge time. Edit `IMPLEMENTATION_PLAN.md` itself only to change its stable sections. When an item's work changes later, update its own plan.d file. The same rule applies to any other list that many branches would extend: add a new file or edit the item's own row in place, never append to a shared tail. Branches opened before this rule that appended a line to a folder plan resolve the resulting conflict by merging `origin/main` and moving their line into their plan.d file.
- Judge compatibility-wrapper results by their exit code; since the PS 5.1 handle fix a blank or non-zero exit is a real failure. The JSON report (`Accepted`) remains the evidence of record.

### Cloud routines (unattended, PC off)

Two scheduled cloud routines run unattended, day and night: **CosmicRift development (every 4h)** (:15 past 1, 5, 9, 13, 17 and 21 o'clock Chicago time) and **CosmicRift senior reviewer (every 4h)** (:45 past 3, 7, 11, 15, 19 and 23 o'clock). They also wake each other (see "Hand-over keys"), so a finished item is reviewed and a review with findings is reworked without waiting for the next slot. Both start from the latest `origin/main` and obey every rule above. All review traffic goes through GitHub pull requests on `RunDLL32-Steve/CosmicRift-Mshra`; use the REST API (`gh api repos/RunDLL32-Steve/CosmicRift-Mshra/...`), because GraphQL-based `gh pr` commands are unavailable in cloud sessions.

- **Branches and claims.** One item per branch named `cloud/<lowercase RT-ID>-<slug>`, one RT-ID per branch. Any RT-ID touched by an unmerged `origin/cloud/*` branch (name, commits, log) or an open pull request is claimed and must not be started again. A branch that truly depends on an unmerged cloud branch is cut from it and says so in its log and its PR. Cloud routines push only their own `cloud/*` branch and never push main.
- **Pull request per branch.** As soon as a branch carries real work, the developer opens a PR (`POST /pulls`) whose base is `main`, or the parent `cloud/*` branch when stacked. Title `RT-F### <summary>`; the body lists RT-IDs, queue ids, gate items, stacked-on, acceptance clauses done vs remaining, files touched, tests run with numbers, and what is "not verified in cloud - local CI required". Either routine opens a missing PR for any existing `cloud/*` branch that has work but no PR.
- **Hand-over keys: BBQ and cooked.** These two words are how work changes hands, so no one has to guess whether a branch is finished or a comment wants an answer. They are matched by `python scripts/review-queue.py` (tests: `python -m unittest scripts/test_review_queue.py`), which both routines run instead of reading the labels by eye.
  - **BBQ.** The developer's last commit before opening a PR, and again after every rework or conflict push, is an empty commit whose subject starts with the word `BBQ` (`git commit --allow-empty -m "BBQ RT-F033 ready for review"`). Do it only when the item is finished, tests are run and the tracker check is consistent, and add no attribution trailer. A branch whose newest developer commit is not BBQ is still being worked on and is not reviewed. The reviewer's own log-mirror commits (subject starts with `REVIEW`) do not count as developer commits. Any developer commit after a BBQ commit reopens the branch until the next BBQ.
  - **cooked.** Every comment the developer leaves on a PR (summary, thread reply, conflict note) ends with the word `cooked` as its last word, left only once the item is finished and the BBQ commit is pushed. The reviewer treats any comment whose last word is `cooked` (case-insensitive; a trailing `---`/`_Generated by ..._` footer, punctuation and bold or italic markers are ignored) and that is newer than its latest review as a summons and reviews that PR, answering a comment from the owner too. The reviewer never ends a comment with that word, so the loop cannot trigger itself.
  - **Wake-ups.** After the BBQ commit and the cooked comment the developer fires the reviewer routine (`fire_trigger`, text names the PR numbers); after posting a review that sets `review-changes-requested` the reviewer fires the development routine. Fire a routine only when its `last_run` in `list_triggers` is not still running (status pending) and it did not start in the last 20 minutes; otherwise rely on the schedule. A reviewer run ends by running `scripts/review-queue.py` once more and continuing if a PR was queued meanwhile.
  - **Transition.** A PR that has no BBQ commit in its history but is labelled `review-pending` is reviewed as legacy whenever it has developer commits that no review covers (so work opened before this rule, or reworked by a routine that does not write BBQ commits yet, is not stranded). Once a PR has a BBQ commit it follows the BBQ and cooked rules only.
- **Labels are the review status.** Exactly one of `review-pending`, `review-changes-requested`, `review-approved`, `needs-human` is on each open PR (create missing labels via `POST /labels`). The branch log's first line `Review status: ...` mirrors the label.
- **Branch log.** `docs/development-log/cloud/<branch with / replaced by ->.md` records scope and acceptance criteria, RT-IDs claimed, files touched, status (done/wip/blocked), verified and unverified results with numbers, and the resume point.
- **Review loop.** The author never reviews or approves its own work. The senior reviewer reviews the PRs that `scripts/review-queue.py` lists (BBQ ready or cooked, see "Hand-over keys"), stacked bases first, oldest first. It reads the full PR diff, runs what it can, and posts a GitHub review (`POST /pulls/{n}/reviews`, event `COMMENT`, because one account cannot approve its own PR) with an inline comment per finding (file:line, severity blocker/major/minor/nit, evidence, expected fix) and a summary giving round N and the verdict. It then sets the label. APPROVED requires no blockers or majors and a match to scope. The reviewer never fixes the author's code. Branches whose log said APPROVED under the old flow still get one PR review pass before merge.
- **Rework.** The next development run takes the oldest `review-changes-requested` PR before any new item. It fixes every blocker and major on that same branch, replies to every review comment (`POST /pulls/{n}/comments/{id}/replies`: fixed in `<sha>` / disputed with reasoning / cannot fix and why), pushes the fixes and then the BBQ commit, posts a summary comment ending with the word `cooked`, sets `review-pending` and wakes the reviewer. Only the reviewer resolves threads, after checking each fix. After round 3 with blockers open the label becomes `needs-human`.
- **Review quality protocol (binding on every reviewer and developer, local and cloud).** A PR is merged only after a reviewer has read the whole diff against the claimed scope and acceptance clauses and the developer has had the chance to fix what was found; a bare approval, an approval of an older head, or merging a PR that was never reviewed is a process violation and the merge must not happen. (1) **Findings must be actionable.** Every finding is an inline comment that quotes the exact lines concerned (a fenced block with the file path and line numbers, or the lines the comment is anchored to), gives a finding id (R<round>-<n>), the severity (blocker/major/minor/nit), WHY it is wrong (the acceptance clause, scope sentence, rule or evidence it violates), and EXPLICIT fix instructions: what to change, the result the reviewer expects, and which check shows it is done. A GitHub suggestion block is used when the fix is a few lines. A finding that only says something is wrong is invalid and must be rewritten. (2) **The originating agent fixes it.** The branch's author fixes every blocker and major on the same branch, at the same or a stronger model/effort per the matrix; if the author cannot (it disputes, is blocked, or has failed twice) the work is escalated to a higher tier per the matrix and the PR says so. The author replies in each thread with the finding id and `Fixed in <sha>`, `Disputed: <reasoning>` or `Cannot fix: <why>`. (3) **Follow-up file list.** After each rework push the developer posts one PR comment `Files updated after review round N` that lists EVERY file changed since the reviewed head (take it from `git diff --name-status <reviewed head>..<new head>`), one line per file naming the finding id(s) it answers and what changed. A changed file missing from the list, or a listed file with no change, is itself a finding. (4) **Re-review.** The reviewer re-reviews the new head: it checks the list against the real diff, verifies each fix against its own instructions in the original finding, re-runs the applicable checks, and re-reads the context it started from (the PR's stated scope, the RT-ID acceptance clauses, the master plan and the project goals) to confirm the fixed work still supports that scope and goal and did not widen or drift from it. The re-review comment gives a per-finding verdict (fixed, not fixed with new instructions, or disputed and accepted). Only the reviewer resolves threads. (5) **Approval needs evidence.** The approving review lists, per acceptance clause, what was checked and how, and the checks it ran with numbers. The merge gate additionally requires that the approving review is the newest review on the PR, that every blocker/major thread is resolved, and that no commit other than the reviewer's log mirror or an empty BBQ marker follows it.
- **Merge gate.** The senior reviewer merges a PR (`PUT /pulls/{n}/merge`, `merge_method: merge`, `sha` = the reviewed head) only when ALL hold: its own verdict is APPROVED for that exact head commit; the `Build and validate First Contact` check run on that head concluded `success`; the PR is mergeable with no conflicts; its base is `main` (stacked parents merge first, then the child is retargeted with `PATCH /pulls/{n}` base `main` and re-checked); `python scripts/check-trackers.py` prints TRACKERS_CONSISTENT; and the diff touches none of `AGENTS.md`, `.github/`, `scripts/verify.ps1`, `scripts/bootstrap.ps1`, `scripts/check-trackers.py`, `toolchain.lock.json`, canonical original assets, `data/original` or `.tools/references`. A PR touching any of those, or containing secrets, is labelled `needs-human` and left for the owner. Never squash or rebase (stacked children share commits), never force-push, never delete branches. After merging, retarget each child PR to `main`. **Serialized merging:** merge at most one PR at a time; after each merge, re-fetch `main` and re-verify the next PR (mergeable, CI on the new base, `check-trackers.py`) before merging it. **Stale approvals:** an approval covers only the exact reviewed head; any later commit, including a conflict-resolution merge that changes more than the conflict markers, voids it and the PR returns to `review-pending` for a fresh review.
- **CI scope.** GitHub Actions runs `scripts/verify.ps1` on Windows but has no original assets, so original-data oracle tests skip there. The reviewer still reproduces asset-dependent claims itself and records what neither it nor CI could verify.
- **Verification limits.** Cloud runs lack the ignored local toolchain (`.tools/` SDKs, Godot, pinned upstream and original assets). Anything a cloud run cannot test is recorded as "not verified in cloud - local CI required" and never marked complete; results are never fabricated.
- **Stop conditions.** Stop and write the resume point to the branch log when a task needs desktop interaction, an authentication ticket, a user decision or a toolchain the cloud lacks.

### Batch review trigger — October 18, 2026 (applies to every agent: Claude, Codex, local and cloud)

This overrides the 4-hourly reviewer schedule and the "wake the reviewer after each BBQ/cooked" step above. The review process itself (review quality protocol, merge gate, BBQ/cooked keys, labels) is unchanged.

- **Reviewers do not run on a schedule.** A review run starts only when (a) the count of open `cloud/*` PRs labelled `review-pending` reaches **15**, or (b) the user starts it manually.
- **The developer that opens the PR that makes the count 15 starts the reviewer** (after the BBQ commit and label are in place). Count with `gh api repos/RunDLL32-Steve/CosmicRift-Mshra/pulls?state=open` (paginated). Do not start it below 15, and not again while a review run is in progress or started in the last 60 minutes. Claude uses `mcp__scheduled-tasks__run_scheduled_task` with `cosmicrift-local-reviewer`; Codex starts its own review agent (a newly started agent that did not author the PRs) with the same instructions. If the reviewer cannot be started, record it in the report and leave the PRs `review-pending` for the user.
- **A triggered run reviews every `review-pending` PR**, stacked bases first, then oldest first: full diff against scope and acceptance clauses, applicable local checks, protocol and merge gate as above, one merge at a time. If it must stop (usage limit), write the PRs reviewed and remaining to the branch logs and report.
- Reviewers no longer wake the development routine; rework of `review-changes-requested` PRs happens on the development task's next run.
- The author never reviews or merges its own work, in any agent.
